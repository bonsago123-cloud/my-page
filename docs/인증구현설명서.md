# 인증 구현 설명서 — 과제 8 (원본 my-page 기반)

> 상태: 로컬 코드/단위 테스트 완료, GitHub 직접 푸시·배포·실제 패스키 등록 검증은 **미완료**. 이 문서는 제출 전 검증 양식입니다.

## ① 무엇으로 붙였나
기존 `bonsago123-cloud/my-page`의 원본 HTML을 유지하고 Express 5 + `@simplewebauthn/server` 및 `@simplewebauthn/browser` 라이브러리로 패스키 인증 영역을 추가합니다. 로컬 SQLite, 배포용 PostgreSQL을 사용합니다.

## ② 왜 이 기술을 골랐나
WebAuthn 라이브러리로 등록·인증 서명과 RP ID·origin 검증을 서버에서 처리합니다. GitHub Pages의 정적 파일만으로는 DB의 비공개 데이터·세션을 안전하게 지킬 수 없으므로 별도 서버가 필요합니다.

## ③ 어디를 어떻게 고쳤나
- 공개 페이지: GitHub 원본 `index.html` (새로 디자인하지 않음); `scripts/apply-task8.mjs`로 비공개 구획·메뉴 추가
- 패스키 화면: `public/passkey.js`와 `public/passkey.css`
- 등록: `src/app.mjs` `/api/registration/options`, `/api/registration/verify`
- 로그인: `src/app.mjs` `/api/authentication/options`, `/api/authentication/verify`
- 로그아웃: `src/app.mjs` `/api/logout`
- 비공개 조회: `src/app.mjs` `/api/private`, `/api/private/:userId`
- 패스키 등록 목록과 삭제: `src/app.mjs` `/api/passkeys`
- 챌린지의 단발성 소비: `src/services.mjs` `consumeChallenge()`
- 서버 저장: `src/db.mjs`의 `passkeys.public_key` (base64url COSE 공개키)

실제 Passkey 저장소 두 개를 서로 독립적으로 준비하지 못하면 동시에 둘을 분실했을 때 계정 복구 경로가 없습니다. 마지막 한 개는 삭제를 막지만, 패스키 저장소 분실까지 해결하는 것은 아닙니다. 도메인을 변경하면 기존 RP ID로 등록한 패스키를 새 도메인에서 자동으로 사용할 수도 없습니다.
