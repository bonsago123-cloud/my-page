## ① 무엇으로 붙였나
- 기존 정적 자기소개에 별도 패스키 인증 UI를 연결하고, Vercel에서 Express 기반 WebAuthn API를 운영합니다.
- WebAuthn 등록·인증: `@simplewebauthn/browser` 및 `@simplewebauthn/server` 라이브러리.
- 인증 메타데이터 및 가상 비공개 기록: Neon PostgreSQL.
- 로그인 유지: HttpOnly 쿠키를 통한 서버 세션. 세션 원문은 DB에 저장하지 않고 해시를 저장하도록 구현되어 있습니다.
- 서버에는 인증 자격 증명 ID와 공개키를 보관하며, 개인키를 요구하거나 보관하지 않도록 구현되어 있습니다.

## ② 왜 그걸 골랐나
- 비밀번호 없이 공개키 서명으로 로그인하는 과제의 WebAuthn 요구사항에 맞추기 위해서입니다.
- 공개 영역은 누구에게나 보이고 비공개 자료는 인증된 서버 요청에서만 내려받도록 구분했습니다.
- 브라우저에 내장된 패스키 인터페이스를 사용하면 Windows Hello나 별도 인증기를 사용할 수 있습니다.
- 초기 등록·삭제 실습에서 기존 패스키를 유지할 수 있도록 마지막 키 삭제를 방지하는 정책을 적용했습니다.

## ④-6. 추가 수행한 격리 HTTP 보안 테스트 — 2/2 통과 (2026-11-18)

테스트 코드는 `검증코드/extra-security.test.mjs`, 실제 실행 로그는 `검증코드/격리_HTTP_실행결과.txt`, 재현 방법과 제한은 `검증코드/검증방법과한계.md`에 동봉했습니다.

- **챌린지 재사용 방지:** 로그인 옵션 2회 발급 HTTP 200/200 → 발급된 챌린지가 서로 다름. 테스트용 모의 인증기 통과 HTTP 200 → 동일 `ticket`의 두 번째 인증 요청 HTTP **409** (`챌린지가 이미 사용되었거나 만료되었습니다.`).
- **계정 A/B 양방향 접근 차단:** `alpha-lab` A 본인 자료 GET **200**, B 자료 명시 URL **403**. `beta-lab` B 본인 자료 GET **200**, A 자료 명시 URL **403**. 차단 전후 A/B 각각 비공개 자료 **3→3건**으로 변동 없음. `accountId` 쿼리를 다른 계정으로 바꿔도 자신의 자료만 반환됨.
- **검증의 경계:** 운영 DB·기존 패스키를 변경하지 않은 **로컬 임시 SQLite DB와 HTTP 테스트**입니다. 서버 라우팅·접근 제어는 실제 소스 로직을 이용했지만 WebAuthn 서명 검증과 실행 당시의 Express 운반 계층은 **모의 구현**입니다. 이 결과를 운영 실제 패스키 2개를 사용한 종단간 테스트로 주장하지 않습니다.
- **사용자 직접 검증:** 삭제한 패스키로 로그인되지 않음을 사용자가 별도로 확인했다고 밝혔습니다. 해당 HTTP 거절 패킷은 제출된 스크린샷에 포함되지 않아 진술과 네트워크 증거를 구분합니다.

## ⑥ 아직 못 막은 것 / 한계
1. **독립적인 패스키 저장소 분실 시 복구:** 마지막 패스키 삭제는 막지만, 인증기 자체를 잃어버려 실제로 모든 개인키를 사용할 수 없게 되면 자동 복구 경로가 없습니다. 과제에서 요구한 패스키 분실 위험과 직접 관련된 한계입니다.
2. **서버 연결 장애 복구 탄력성:** 실제 실습 중 PostgreSQL 연결 종료 오류로 HTTP 500 장애가 발생했고, 재배포로 일시 복구했습니다. 자동 재시도 등 근본적인 복구 동작을 운영 수준에서 모두 검증하지 못했습니다.
3. **검증 범위 한계:** 실운영 HTTPS API에서 새 합성 시험 인증기의 WebAuthn 등록·서명·재사용 차단·양방향 자료 차단은 검증했습니다. 단, 실물 Windows Hello 기기 두 개를 이용한 계정 간 교차 테스트는 아니며, 기존 운영 계정(567 등)의 인증 정보는 이용하지 않았습니다.

## 제출 직전 주의사항
- **검증 환경을 구분하세요.** 격리 HTTP 테스트는 모의 WebAuthn 인증기였지만, 뒤이어 수행한 운영 HTTPS API 테스트에는 실제 P-256 키쌍과 서명이 사용됐습니다. 이는 Windows Hello 실물 기기 자체로 검증했다는 뜻은 아닙니다.
- 개인키·세션 쿠키·챌린지 티켓 전체를 스크린샷이나 문서에 넣지 않습니다.
- 이 보고서에 들어간 URL과 이미지 외에 서버 비밀값·접속 문자열은 포함하지 않았습니다.
- 기존 자기소개 내용 중 실명 등 정보가 과제의 개인정보 금지 조건을 위반하는지 최종 점검해야 합니다.


## ④-7. 추가 실운영 WebAuthn HTTPS 검증 — 통과 (2026-11-18, KST)

**대상:** `https://my-page-passkey-chan2-efc7.vercel.app` 실운영 Vercel API 및 연결된 Neon DB. 독립된 Vercel Sandbox에서 Node.js 22의 `crypto`로 P-256 공개키/개인키 쌍 두 개를 만들고, WebAuthn 규격의 CBOR `attestationObject`(`fmt:none`), `authenticatorData`, `clientDataJSON`, ECDSA-SHA256 서명을 생성하여 실제 `/api/registration/verify`, `/api/authentication/verify`에 전송. 서버의 WebAuthn 검증 함수를 모의로 교체하지 않았음.

**한계:** 암호학적으로 유효한 소프트웨어 생성 시험 인증기 WebAuthn 인증을 실서버에서 확인한 것이며, 실제 Windows Hello/휴대전화의 플랫폼 UI 동작을 종단간 검증한 것은 아닙니다. 또한 삭제된 패스키 실제 로그인 실패는 사용자 직접 검증 진술을 반영하고, 해당 실패 요청의 상세 네트워크 캡처는 미첨부입니다.
