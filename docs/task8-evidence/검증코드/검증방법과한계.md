# 추가 보안 검사 실행 방법과 범위

## 검증 대상

- 검사 대상: 과제 8 패스키 부가기능의 `src/app.mjs`, `src/db.mjs`, `src/services.mjs`, `src/security.mjs`에서 구현한 인증 챌린지 소비 및 계정별 비공개 자료 접근 제어 로직
- 실행 위치: 운영 Vercel/Neon과 연결되지 않은 **별도 Node.js 로컬 HTTP 프로세스 및 임시 SQLite DB**
- 검사 계정: 임시 가상 계정 `alpha-lab`, `beta-lab` (각각 가상 비공개 자료 3건)
- 요청/응답: 실제 HTTP GET/POST. `app.mjs`의 라우트 핸들러, `services.mjs`의 일회용 챌린지 및 세션 함수, `db.mjs`의 SQLite 어댑터 사용
- WebAuthn 검증기: **모의 구현**. 따라서 진짜 하드웨어 패스키 서명 검증이나 운영 환경 서명 성공을 증명하지는 않음
- 로컬 실행 환경 제약 때문에, 실행 당시 Express HTTP 운반 계층과 `@simplewebauthn/server` 모듈 로딩은 임시 스텁으로 대체했음. 체크인용 `extra-security.test.mjs`는 실제 라이브러리를 설치한 개발 환경에서도 동작하도록 설계했지만, 그 환경에서의 실행은 아직 확인되지 않음
- 운영 사이트의 두 계정으로 실제 패스키 로그인한 후 교차 접근 요청을 수행한 결과는 **별도 미검증**

## 검증 결과 (2026-11-18)

| 검증 요청 | HTTP/상태 | 결과 |
|---|---|---|
| A의 첫 로그인 옵션 발급 | 200 | 챌린지 발급 |
| A의 두 번째 로그인 옵션 발급 | 200 | 첫 챌린지와 다른 값 |
| A의 최초 인증 응답 (모의 검증기 통과) | 200 | 인증 통과 분기 확인 |
| 동일한 인증 `ticket` 두 번째 제출 | **409** | `챌린지가 이미 사용되었거나 만료되었습니다.` |
| A의 자기 `/api/private` 요청 | **200** | 3건 |
| A의 `/api/private/{B_ID}` 요청 | **403** | 거절 |
| B의 자기 `/api/private` 요청 | **200** | 3건 |
| B의 `/api/private/{A_ID}` 요청 | **403** | 거절 |
| A의 `/api/private?accountId={B_ID}` 요청 | **200** | A 자신의 자료 반환 |
| B의 `/api/private?accountId={A_ID}` 요청 | **200** | B 자신의 자료 반환 |
| A 자료 건수(거절 전/후) | 3/3 | 변경 없음 |
| B 자료 건수(거절 전/후) | 3/3 | 변경 없음 |
| 비인증 `/api/private/{B_ID}` 요청 | **401** | 거절 |

## 재현

이 파일과 같은 폴더의 `extra-security.test.mjs`를 원본 저장소의 `test/extra-security.test.mjs`로 복사하고, 해당 프로젝트에서 `npm ci`로 실제 의존성을 설치한 뒤 `node --test test/extra-security.test.mjs` 실행. 테스트는 운영 DATABASE_URL을 사용하지 않고 시스템 임시 경로에 SQLite를 만들어 끝나면 삭제함.

원본 프로덕션 DB는 쓰거나 변경하지 않았음. 요청 헤더의 실제 로그인 쿠키, 패스키 개인키, 챌린지 티켓 원문은 출력 로그에 포함되지 않음.

## 남은 제한

과제에서 요구한 **실제 운영 사이트에서 A/B 양방향 로그인 후 HTTP 403** 및 **실제 패스키로 정상 인증 뒤 동일 챌린지 재사용**은 별도 실운영 요청 기록이 필요함. 이 격리 검사를 실운영 검증으로 표현하면 안 됨.
